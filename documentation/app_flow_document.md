# App Flow Document for Multitenant Restaurant SaaS

## Onboarding and Sign-In/Sign-Up

A new user lands on the public entry point of the application, which features a simple landing page presenting options to sign in or sign up. Choosing to sign up directs the user to an email registration form where they enter their email address and a password. Upon submission, the system sends a confirmation email containing a verification link. Clicking that link completes the account creation process and redirects the user to the sign-in page. Restaurant Owners can then create their first tenant entity. Restaurant Staff users never sign up directly; they receive an invitation email from an Owner which includes a unique signup link. That link takes them to a pre-filled registration form that, once completed, activates their staff account. The Super Admin account is provisioned separately in the system database and uses the same sign-in workflow as Owners. On the sign-in page, returning users enter their email and password and click sign in. If they forget their password, they can click “Forgot Password,” supply their email address, and receive a secure reset link. Following that link lets them enter a new password and then sign in again. Every authenticated page has a sign-out link in the header; clicking it ends the session and returns the user to the sign-in page.

## Main Dashboard or Home Page

After signing in, the user is taken to the protected dashboard area at `/dashboard`. The first thing they see is a header bar and a vertical sidebar. The header displays the application name, a theme toggle switch, a notifications icon, and a profile menu that offers links to Settings and Sign Out. The sidebar lists navigation items tailored to the user’s role. A Restaurant Owner sees links to Menu, Staff, Analytics, and Settings. Staff members see links to Kitchen Orders and Table Status. The Super Admin sees links to Tenants, Subscriptions, System Health, and Settings. Clicking any item in the sidebar loads that section into the main content area. The dashboard uses a responsive grid layout so that on smaller screens the sidebar collapses behind a menu button.

## Detailed Feature Flows and Page Transitions

When a Restaurant Owner clicks the Menu link, the app navigates to `/dashboard/menu`. This page fetches the owner’s menu items from the database and displays them as cards with images, names, and prices. At the top of the page is an Add Item button. Clicking it opens a modal form where the owner types a name, description, price, and uploads an image. Submitting the form calls an API route to save the new item and automatically refreshes the list on success. To edit an item, the owner clicks its card, which transforms the display into inline editable fields. Saving updates the database and returns the card to view mode. Deleting an item prompts a confirmation dialog before removing it.

In the Staff section, Owners can invite team members by going to `/dashboard/staff` and filling out an invite form. An email is sent with a secure link. When a Staff member follows that link, they complete a simple registration page and are then routed to their role‐specific dashboard.

Kitchen Staff click the Kitchen Orders link to land on `/dashboard/kitchen`. This page subscribes to real-time updates via WebSockets so that new orders appear instantly as cards in a queue. Each order card shows table number, items ordered, and special notes. Staff can click a card to change its status to In Progress or Completed, which triggers both a database update and a UI animation. Completed orders fade out of the active queue and move to an archive.

Waiters select Table Status in the sidebar and go to `/dashboard/tables`. They see a floor plan layout with colored indicators for each table’s status. Clicking a table opens a slide-over panel showing order details or allowing the waiter to initiate a new guest order entry by selecting items from the menu and sending the order to the kitchen in real time.

The Super Admin logs in and is directed to `/admin` instead of `/dashboard`. The Admin layout shares the same header but features a specialized sidebar with Tenants, Subscriptions, and System Health. Under Tenants, the Super Admin can view all restaurant tenants, search by name, and click Add Tenant. That opens a form for the new restaurant’s name, slug, and Owner email. Submitting creates the tenant record and triggers an Owner invite email. In Subscriptions, the Super Admin integrates with a payment provider, setting or updating each tenant’s plan. System Health shows operational metrics and logs.

Public customers never sign in. They access the menu via a QR code that directs their browser to `/r/[restaurantSlug]/[tableId]`. That page displays the restaurant’s public menu, loaded from the database, grouped by categories. Items have Add to Basket buttons. Tapping one adds it to a floating basket icon in the corner. When ready, the customer clicks View Basket, reviews or modifies quantities in a basket slide-over, and then clicks Place Order. The app collects the tableId from the URL and sends an order payload to an API route. Upon success, the screen transitions to a confirmation page showing the estimated wait time. Meanwhile, kitchen dashboards update instantly.

## Settings and Account Management

Every user can open the Settings page by clicking their profile avatar in the header and selecting Settings. On this page they can update personal information such as display name and email address, change their password, and toggle between light and dark mode using the integrated theming switch. Owners have an additional Billing tab where they can view their subscription plan, next billing date, and click buttons to update payment methods or upgrade their plan. Staff members see only their personal preferences and password change options. Super Admins have advanced account settings for system reporting intervals and API key management. Saving any settings initiates an API call and displays a success toast. A Back to Dashboard link at the top of the Settings page returns the user to their previous dashboard view.

## Error States and Alternate Paths

If a user enters incorrect credentials on sign in, an error banner appears above the form stating “Invalid email or password.” On the sign-up form, leaving any required field blank shows a red helper message below each field. If the forgot-password email address is not recognized, the form still displays a generic success message for security reasons and does not reveal whether the email exists. When an invitation link for a staff signup has expired or been used, the user sees an error page explaining the link is invalid and a button to request a new invite from their Owner. Within the dashboard, if a user tries to navigate to a section they are not permitted to view (for example, a staff member attempting to access Analytics), they see a 403 dialog screen with explanatory text and a button back to the permitted home section. If the client loses network connectivity while performing an action, a full-screen offline indicator appears with a Retry button that automatically reattempts the last API request when the connection is restored. Form submissions that fail due to server errors display a toast notification reading “Something went wrong. Please try again.” and log the detailed error in the browser console for debugging.

## Conclusion and Overall App Journey

In summary, a Restaurant Owner finds the app’s landing page, signs up via email, verifies their account, and is guided to create their first tenant. They build menus, invite staff, and monitor orders in real time. Staff teammates receive invitation links, set up their credentials, and then handle orders from either the Kitchen or Table Status views. Customers scan QR codes to browse menus and place orders without needing to log in. The Super Admin oversees tenants and subscriptions from the Admin portal. Throughout every step, clear navigation, consistent theming, and robust error handling ensure a smooth and predictable experience. From sign-up to daily operations, the application’s flow connects each page and feature in a cohesive journey that meets the multitenant SaaS requirements for modern restaurant management.
